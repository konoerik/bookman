# Architecture

## Quick Reference
**Stack:** Python 3.10+, uv, pytest, ruff, mypy (strict)
**Entry point:** `src/bookman/__init__.py` (exports `Library`, `Book`, `BookFormat`, `FormatKind`, `MatchBasis`, `UnsupportedFormatError`; the lookup seam `MetadataSource`, `Candidate`, `MetadataSourceError`, `OpenLibrarySource`, `NullSource`; every error type under `BookmanError` (`ParseError`/`BadEpubError`/`BadPdfError`, `UnsupportedFormatError`, `MetadataSourceError`/`OpenLibraryError`, `CatalogError`, `ConfigError`, `LibraryNotConfiguredError`); `supported_suffixes`; and the config API: `Config`, `config_path`, `load_config`, `save_config`, `resolve_library`)
**Key paths:** `src/bookman/library.py` (Library: import_file/scan/search — the main entry point), `src/bookman/config.py` (persisted library location, shared by CLI and TUI), `src/bookman/cli.py` (`bookman` console script), `src/bookman/models.py` (Book/BookFormat; `Book.id` is identity, ADR-17), `src/bookman/formats/` (per-format parsers), `src/bookman/identify/` (ISBN, Open Library lookup/search, the `match_basis` same-book rule, and `identify()` which ties them together), `src/bookman/storage/` (catalog + index)
**Key constraints:** one runtime dependency (`pypdf`); everything else (EPUB parsing, HTTP) is stdlib-only; managed library folder is flat (`Library/<Title>/`), no author-level nesting
**Identification spec:** `docs/IDENTIFICATION.md` — the intended Identify/Group/match-rule behavior as a Mermaid flowchart plus a normative YAML block with stable step IDs (MATCH-0..3, IDENT-1..6, GROUP-1..4). Written from the ADRs, never from the code, so it is the source of truth to check the code against; `docs/FEATURES.md` Part I is the conformance report against it, and its `Step` column maps each scenario to a step. Change it (with an ADR) before changing identification behavior. Loaded on demand by the `matching` skill (`.claude/skills/matching/`), which triggers on matching/grouping work rather than every session; `/matching` invokes it by hand. The code is bound to it by `bookman.identify.SPEC_VERSION`, a `Spec:` line on every implementing function, and `tests/test_spec_conformance.py` (ADR-16).
**Patterns:** value objects in `models.py`; format parsers are plain callables satisfying the `FormatParser` Protocol and registered by suffix in `bookman.formats` (`register`/`parser_for`/`supported_suffixes`); metadata lookups go through the `MetadataSource` Protocol injected into `Library` (ADR-13); `storage.store.Catalog` is the one persistence boundary over metadata.json (source of truth) + the disposable sqlite3 index (ADR-12); every raised exception is a `BookmanError`; stub-first for new public functions per `.claude/claudify.md`

### ADR-1: Managed library uses a flat, title-named directory layout
**Date:** 2026-09-13
**Context:** Need a stable on-disk identity for a "book" that groups multiple format files (EPUB/PDF/MOBI) of the same title. Calibre's Author/Title nesting was the obvious default, but author is often unreliable at import time (bundle purchases rarely carry clean author metadata upfront).
**Decision:** Managed library is flat: `Library/<Title>/` holding all format files, `cover.png`, and a `metadata.json` sidecar for that book. No author-level directory.
**Alternatives considered:** Author/Title nesting (Calibre-style); Author/Series/Title nesting.
**Consequences:** Simpler import path (no dependency on author identification before placement). Reorganizing by author later (if ever wanted) becomes a separate helper/reindex script driven by a lookup index, not a core library concern — deferred, tracked in ROADMAP.

### ADR-2: v1 format scope is EPUB + PDF; MOBI follows as the next slice
**Date:** 2026-09-13
**Context:** Real-world bundles (e.g. Humble Bundle) commonly include EPUB, PDF, and sometimes MOBI of the same title. MOBI has no clean pure-Python parsing story (no well-maintained stdlib-friendly library), which would delay a working end-to-end import flow.
**Decision:** Ship EPUB and PDF parsing behind the `FormatParser` protocol first. Add MOBI as an additional parser module once the core scan/identify/organize flow is proven, without changing the public API shape.
**Alternatives considered:** All three formats from day one.
**Consequences:** `FormatKind.MOBI` exists in the enum now (so the data model doesn't need a breaking change later), but no MOBI parser ships until a follow-up slice.
**Amendment (2026-09-18):** that follow-up slice is deprioritized below v1.0. MOBI is Mobipocket — Amazon-only since 2005, and Amazon itself has moved off it (Send to Kindle stopped accepting MOBI in 2022; current Kindles use AZW3/KFX). Combined with the "no clean pure-Python parsing story" noted above and ADR-3's dependency policy, it is the most expensive format work available for the least current value. Unparsed MOBI files are skipped and reported, not failed (FEATURES H6), which stands as the v1.0 behavior. The decision is sequencing only: nothing in this ADR's Decision changes, and `FormatKind.MOBI` stays put. Revisit if a real bundle ships MOBI-only titles.

### ADR-3: Single new runtime dependency — pypdf; EPUB and HTTP stay stdlib-only
**Date:** 2026-09-13
**Context:** CLAUDE.md requires discussing any new runtime dependency before adding it. EPUB is a zip of XHTML + an OPF XML manifest — parseable with stdlib `zipfile` + `xml.etree.ElementTree` without a library like `ebooklib`. PDF metadata/text extraction has no reasonable pure-stdlib option. Online lookup (Open Library) is simple JSON-over-HTTPS GETs, coverable with stdlib `urllib.request`.
**Decision:** Add `pypdf` as the only new runtime dependency. Verified its base install pulls in zero required third-party packages (only a conditional `typing_extensions` backport on Python <3.11, itself not applicable to bookman's actual runtime beyond a redundant marker). EPUB parsing and Open Library HTTP calls use the standard library.
**Alternatives considered:** `ebooklib` for EPUB; `requests`/`httpx` for HTTP.
**Consequences:** Dependency footprint stays at one direct runtime package. If PDF text extraction quality proves insufficient for ISBN detection in practice, this decision may need revisiting.

### ADR-4: Identify workflow is auto-lookup with a review flag, not a blocking confirmation
**Date:** 2026-09-13
**Context:** Need to decide how aggressively the library acts on metadata/cover matches found during import, given the TUI (not yet built) is the eventual place a human reviews results.
**Decision:** On import, the library extracts/guesses an ISBN, queries Open Library automatically, and writes the resulting metadata + cover — but records match confidence (`MatchConfidence.VERIFIED` / `NEEDS_REVIEW`) on the `Book` so a low-confidence result can be surfaced and corrected later (by the TUI, or a future CLI) rather than blocking import.
**Alternatives considered:** Always pause for interactive confirmation before writing anything (Calibre-style wizard); no auto-lookup at all, leaving lookup entirely to the TUI layer.
**Consequences:** The library can run non-interactively end-to-end (useful for batch imports of a 20-30 file bundle drop), at the cost of sometimes writing a wrong guess that must be corrected later. `Book.confidence` is now part of the core data model to support this.

### ADR-5: Exact-ISBN-matched confidence only ever upgrades, never auto-downgrades
**Date:** 2026-09-13
**Context:** A fresh-context critique agent (run deliberately outside the authoring session, per `.claude/claudify.md`) found that `Library.import_file`'s confidence logic recomputed `VERIFIED`/`NEEDS_REVIEW` from the *current* import's own Open Library lookup outcome even when the file matched an existing book by exact ISBN — the strongest possible grouping signal. A transient Open Library outage on a second-format import (e.g. adding the PDF after the EPUB was already verified) would silently downgrade an already-`VERIFIED` book back to `NEEDS_REVIEW`, contradicting ADR-4's intent that only genuinely uncertain groupings get flagged.
**Decision:** Confidence assignment now branches on how the folder was matched: a fuzzy title match always sets `NEEDS_REVIEW` (unchanged from ADR-4 — an uncertain grouping is always worth a second look); a new book sets `VERIFIED`/`NEEDS_REVIEW` from this import's lookup outcome (unchanged); an exact ISBN match sets `VERIFIED` if this import's lookup also succeeded, but otherwise leaves the book's existing confidence untouched rather than recomputing it downward. Also fixed in the same pass: a verified lookup on a follow-up format now updates `Book.title` (previously only used for matching, then discarded — a bad first-guess title could persist forever even after a later verified lookup).
**Alternatives considered:** Leaving the original always-recompute behavior (rejected — directly contradicts ADR-4's stated intent and was verifiably wrong); requiring a fresh successful lookup on every import to maintain VERIFIED status (rejected — would make confidence flap on ordinary network flakiness rather than only on genuine grouping uncertainty).
**Consequences:** Confidence is now monotonically non-decreasing for exact-ISBN-matched books absent a fuzzy-match event, which is the behavior ADR-4 originally described. Two related design concerns surfaced by the same critique — the fuzzy-match threshold's real-world reliability, and the lack of a title cross-check before trusting a lookup as VERIFIED — are deliberately not addressed here; see `docs/PLAN.md` Backlog.

### ADR-6: CLI is a thin stdlib-argparse wrapper over `Library`; directory-walk import logic lives in `Library`, not the CLI
**Date:** 2026-09-13
**Context:** Wanted a way to drive bookman (point at a file or folder, import, list, search) without waiting on the separate TUI project. Needed to settle two things CLAUDE.md gates explicitly: which argument-parsing approach to use (a new runtime dependency requires discussion), and where "walk a directory and import every supported file" logic should live.
**Decision:** Built `src/bookman/cli.py` on stdlib `argparse` only, exposed via `[project.scripts] bookman = "bookman.cli:main"`. Three subcommands — `import PATH [--recursive]`, `list [--needs-review]`, `search QUERY` — all take a global `--library/-l` (default: cwd), usable before or after the subcommand. The directory-walk batch-import logic lives in a new `Library.import_directory(directory, *, recursive=False) -> ImportBatchResult`, not in the CLI, so the future TUI gets it for free instead of reimplementing the same loop.
**Alternatives considered:** click/typer for nicer subcommand ergonomics (rejected — new runtime dependency, conflicts with ADR-3's minimal-footprint policy without strong enough justification); doing the folder walk in the CLI only (rejected — TUI would have to duplicate it later).
**Consequences:** `Library`'s public surface grows by `import_directory` and `ImportBatchResult` (minor version bump per CLAUDE.md's semver convention). `bookman` is now usable standalone via `uv run bookman ...` or the installed console script. Along the way, hit and fixed a real argparse pitfall: a subparser parses into its own fresh namespace and unconditionally copies every attribute — including untouched defaults — back onto the parent namespace, which silently discarded a `--library` value given *before* the subcommand (several tests briefly wrote real book folders into the project directory before this was caught via `git status`). Fixed by giving the subparsers' duplicate `--library` option `default=argparse.SUPPRESS`, so only an explicitly-passed value participates in that copy-back.

### ADR-7: `storage.index.search` case-folds via a registered Python function, not SQL `COLLATE NOCASE`
**Date:** 2026-09-13
**Context:** Exercising the new CLI against real, small public-domain EPUBs (checked into `tests/fixtures/books/`, including a Greek title) surfaced that `search("λάρας")` (lowercase) failed to match a book titled `"Λουκής Λάρας"` — a real correctness bug, not a fixture artifact. SQLite's `COLLATE NOCASE` is documented to fold only ASCII `A-Z`/`a-z`; verified directly (`SELECT 'Λάρας' LIKE '%λάρας%' COLLATE NOCASE` returns 0), so `search`'s own documented "case-insensitive substring match" contract silently didn't hold for Greek, Cyrillic, or even accented Latin (`É`/`é`) titles/authors.
**Decision:** Register a Python scalar function (`conn.create_function("casefold", 1, lambda s: (s or "").casefold())`) and compare `casefold(title) LIKE ?` / `casefold(author) LIKE ?` against an already-`str.casefold()`-ed query pattern, instead of relying on SQL-side `COLLATE NOCASE`. Case-folding now happens in Python (Unicode-aware) on both sides of the comparison; the `LIKE` operator only does the (ASCII-agnostic) substring/wildcard matching.
**Alternatives considered:** Loading SQLite's ICU extension for proper Unicode collation (rejected — not available in Python's stdlib `sqlite3` build, would need a compiled extension, against the minimal-dependency-footprint stance in ADR-3); moving search filtering out of SQL entirely into Python over `Library.scan()`'s results (rejected — throws away the point of the sqlite index existing at all, per its own module docstring, for a personal-library-scale dataset it doesn't need to).
**Consequences:** `search` now correctly case-folds any script Python's `str.casefold()` handles. Regression coverage added in `tests/test_index.py` (synthetic Greek title) and `tests/test_real_books.py` (the real Gutenberg fixture) so this can't silently regress. This is the second real bug (after ADR-5) found by testing against something other than purpose-built synthetic fixtures — worth remembering when reviewing future "critique" or exploration passes.

### ADR-8: Library location is a persisted user config in the core package (`bookman.config`), not a per-frontend setting
**Date:** 2026-09-13
**Context:** After the CLI revamp, the remaining usability gap was that every command needed `--library` (or silently defaulted to the current directory, which made `bookman list` in a random folder report an "empty library"). The intended usage model is: install, point bookman at a library folder once, and have every subsequent CLI *and* TUI invocation use it until changed. The open question was whether that "remembered location" belongs to each frontend (CLI keeps a file, TUI keeps its own) or to the core package.
**Decision:** Added a public `bookman.config` module — `Config` (one field, `library: Path`), `config_path()`, `load_config()`, `save_config()`, `resolve_library(explicit=None)`, `LibraryNotConfiguredError` — exported from `bookman/__init__.py`. Resolution order is fixed in the core: explicit override (a `--library` flag or a TUI picker) → `$BOOKMAN_LIBRARY` → the config file → `LibraryNotConfiguredError`. The file is `config.json` in the platform user-config directory (`~/Library/Application Support/bookman/` on macOS, `%APPDATA%\bookman\` on Windows, `$XDG_CONFIG_HOME/bookman/` else), located with stdlib only; `$BOOKMAN_CONFIG` can point at a different file (used by tests and CLI smoke runs to stay isolated from the developer's real config). Writes are atomic and store an absolute, `~`-expanded path. The CLI gained `bookman init <dir>` (create + save) and `bookman config` (show sources and the active library), and dropped the cwd default: a command with no resolvable library errors out with the `init` hint instead of guessing.
**Alternatives considered:** CLI-only config, with the TUI writing its own later (rejected by the user — the setting is central to how the tool is used and would be implemented twice, then drift). A `config.json` in the working directory (rejected — reintroduces the "which directory am I in" ambiguity the change exists to remove). `platformdirs` for the config location (rejected — new runtime dependency for three `if` branches; conflicts with ADR-3). Keeping `Library(root)` reading the config itself (rejected — `Library` stays a pure "operate on this path" object so tests and embedders never touch global state; only frontends call `resolve_library`).
**Consequences:** Public API grows by six symbols (minor version bump per the semver convention). `Library` is unchanged and still takes an explicit root; the contract for any frontend is `Library(resolve_library(user_override))`, and `save_config(Config(library=...))` when the user picks a new location — the TUI gets the same behavior for free. The config schema is a one-key JSON object; if more settings arrive, `Config` grows fields and `load_config` keeps rejecting unknown shapes with a `ValueError` the CLI reports as "bad config file". The single-writer/no-locking stance of the library itself (PLAN.md Backlog) applies to the config file too, which is fine for a personal tool.

### ADR-9: Identification and grouping share one evidence-based match rule; `MatchConfidence` replaced by `Book.identified` / `grouped` / `reviewed`; ISBN-less books identified via Open Library title/author search
**Date:** 2026-09-13
**Context:** Four linked Backlog items, all rooted in `Library.import_file`: (1) grouping used a raw-string difflib ratio ≥ 0.9, verified to fail both ways — "the book of job"/"the book of joel" merge at 0.903 while "Deep Work"/"Deep Work: Rules for Focused Success" split at 0.400 — with no author signal; (2) a successful ISBN lookup overwrote the parsed title/author with no cross-check, so a checksum-passing false-positive ISBN scraped from a PDF would silently replace good data and be marked `VERIFIED`; (3) `MatchConfidence` conflated "are these files the same book?" with "is this metadata right?", and had no "human reviewed, don't re-decide" flag, so a future TUI correction would be clobbered by the next import; (4) files without an ISBN — every Project Gutenberg fixture, and any pre-ISBN classic — had no identification path at all and always landed as `NEEDS_REVIEW` with no cover. The unifying observation: Open Library search returns *candidates*, so adding it requires a "does this candidate agree with what the file says about itself?" rule — which is exactly the missing cross-check in (2), and the same title-normalization + author-agreement logic that (1) needs.
**Decision:** One internal rule, `identify.match.match_basis(file_title, file_author, cand_title, cand_author, *, same_isbn) -> MatchBasis | None`, decides both "this file is this Open Library record" and "this file belongs in this existing folder". Titles are compared after normalization (NFKC, casefold, subtitle after `:`/`;`/spaced dash dropped, trailing `(…)`/`[…]` dropped, leading article dropped, punctuation stripped); authors agree when they share a surname (Last, First reordered; accents stripped; initials and "Anonymous"-style placeholders ignored; a comma is read as Last, First only when one side is a single name token, otherwise as a list). Outcomes: a shared ISBN is `ISBN` unless title *and* author both contradict (the false-positive guard); agreeing authors + agreeing titles (fuzzy ≥ 0.9 on normalized forms) is `TITLE_AUTHOR`; disagreeing authors never match regardless of title; an author missing on either side matches only on an *identical* normalized title, as `TITLE_ONLY`. `identify.resolve.identify(parsed)` runs the ISBN lookup (accepting only if `match_basis` agrees, and discarding a contradicted ISBN so it can't seed a later ISBN grouping), then falls back to `openlibrary.search(title, author)` and takes the strongest-basis candidate, preferring one with a cover; a `TITLE_ONLY` hit supplies the title and cover but not an uncorroborated author over the file's own. `Library._resolve_directory` applies the same rule to existing books (exact ISBN first, then `TITLE_AUTHOR` over `TITLE_ONLY`). The data model replaces `MatchConfidence` with `MatchBasis` (`isbn` > `title_author` > `title_only`) and three `Book` fields: `identified` (how the accepted record matched; None = file-only metadata), `grouped` (the *weakest* basis ever used to join a format into the folder; None = single format), and `reviewed` (human-confirmed; imports add formats and update `grouped` but never overwrite title/author/isbn/cover/`identified`; a `TITLE_ONLY` join clears it because the book's contents changed in a doubtful way). `Book.needs_review` is derived: not reviewed and (`identified` is None or `TITLE_ONLY`, or `grouped` is `TITLE_ONLY`). ADR-5's "never auto-downgrade" survives as: an existing book's identification is replaced only by one at least as strong. metadata.json moves to `"version": 2`; version-1 files are migrated on read (`verified` → `identified=isbn`, `needs_review` → None) and rewritten on next save. `MatchConfidence` is removed from the public API — a breaking change, so the package version goes 0.1.0 → 0.2.0. The CLI's `[NEEDS REVIEW]` marker now says why (`no online match` / `matched by title only` / `grouped by title only`).
**Alternatives considered:** Retuning the fuzzy threshold (rejected — verified there is no value that fixes both failure directions; normalization + a second signal is required). A single three-level confidence enum plus `reviewed` (rejected — it would still hide *why* a book needs a look, which is what a TUI needs to show; evidence-named fields make the reason derivable). A separate `metadata_source` enum (file / openlibrary / manual) as first sketched (folded away — `identified` already carries file-vs-online provenance and match strength, and "manual" collapses into `reviewed`). Adopting an ISBN from a search hit (rejected — editions have many ISBNs and picking one would make `Book.isbn` stop meaning "an ISBN found in a file"). Keeping `reviewed` sacrosanct even on a `TITLE_ONLY` join (rejected — a review covers a state; a doubtful change to that state should resurface the book, while still not overwriting the human's metadata).
**Consequences:** All four Backlog items closed by one change; 199 tests (was 129), including `test_match.py` pinning the Backlog's concrete failure strings and a known limitation (surname-only agreement treats "Frank Herbert" and "Brian Herbert" as the same author). A live run against Open Library on the Gutenberg fixtures now identifies Alice (`title_author`, with cover) and A Christmas Carol (`title_author`, no cover — Open Library only returns cover-less Gutenberg-derived records for that exact long title), matches Lazarillo `title_only` while keeping the file's "Anonymous" over a junk author list, and leaves the Greek title unmatched; follow-ups are noted in PLAN.md Backlog. The library honors `reviewed` but nothing sets it yet — the TUI (or a CLI command) needs a way to mark a book reviewed and correct its metadata. Tests that stub network now patch `bookman.identify.resolve.lookup_by_isbn` / `.search` (title search runs for nearly every import, so the shared guard fixtures stub it to find nothing rather than fail loudly).

### ADR-10: The file's own title wins over Open Library's on an accepted match; format files are named after their folder; a colon sanitizes to " -"
**Date:** 2026-09-15
**Context:** The first real-bundle import (five Humble Bundle books) produced the folder "Software Architecture the Hard Parts": the ISBN lookup agreed with the file, so `identify` took Open Library's crowd-sourced title "Software Architecture : the Hard Parts" verbatim, and `_sanitize_dirname` then deleted the colon. The EPUB and PDF both carried the publisher's clean "Software Architecture: The Hard Parts". Separately, every format file was stored as a hardcoded `book.epub` / `book.pdf`, so a file was meaningless outside its folder (a drag to an e-reader, a stray copy, a `find` listing) and the folder name was the only human-readable handle.
**Decision:** (1) `identify.resolve._accepted` returns `parsed.title or record.title` — once `match_basis` has accepted a record, the two titles are known to agree, and the file's spelling is the publisher's, so the record's title is used only when the file has none. Author and cover still come from the record as before (ADR-9 unchanged). (2) `Library.import_file` stores each format as `<folder name><suffix>` (e.g. `Software Architecture - The Hard Parts.epub`), deriving the name from the folder rather than re-sanitizing the title, so every format of a book shares one spelling even when a later format's parsed title differs slightly; when a format is re-imported under a different filename the old file is unlinked, which also migrates pre-0.3 `book.<ext>` files one format at a time. (3) `_sanitize_dirname` turns `\s*:` into ` -` before dropping the remaining unsafe characters, and strips a leading/trailing `-` along with spaces and dots. (4) On an existing, unreviewed book, a follow-up format replaces the title only on *strictly* stronger identification; on equal evidence the first format's spelling stands (author/ISBN/cover still update). This was invisible before because both formats fetched the same record; with file titles, the PDF's `/Title` (the least reliable source) would otherwise overwrite the EPUB's.
**Alternatives considered:** Keeping Open Library's title and just fixing the colon — rejected because OL's spelling is crowd-sourced and the match rule already proves the two describe the same book, so there's no information gained by preferring it. Recording a `title_source` field so a TUI can offer "use Open Library's title instead" — deferred as YAGNI until the TUI asks. Snake_case filenames (`software_architecture_the_hard_parts.epub`) to sidestep every filesystem quirk — rejected: a snake_case file inside a title-cased folder reads as a mismatch, and it's ugly at library scale; the folder sanitizer already handles the unsafe set, so the file reuses it. Naming files from the resolved title independently of the folder — rejected because two formats with slightly different parsed titles would get different names in the same folder. Replacing `/` with `-` as well ("TCP/IP" → "TCPIP" today) — left as-is; the colon was the observed problem.
**Consequences:** metadata.json's per-format `filename` was already the source of truth, so no schema bump; the only reader that assumed `book.<ext>` was `import_file` itself. Existing libraries migrate lazily — a folder keeps its `book.epub` until that format is re-imported, so a `Title.pdf` can sit beside a `book.epub` in the meantime (acceptable; a one-shot rename command is a possible follow-up if it bothers anyone). Folder names change for any title containing a colon, so re-importing an old library into a fresh root gives different folder names than before. Suite at 214 tests. The rerun on the sample bundle now yields "Software Architecture - The Hard Parts/" holding same-named `.epub`/`.pdf`, with the metadata title "Software Architecture: The Hard Parts". Version goes 0.2.0 → 0.3.0 at the next release (new on-disk layout; `Identification.title` semantics changed).

### ADR-11: A Book's identity is its library folder, exposed as `Book.directory`; no minted id yet
*Superseded in part by ADR-17 (2026-09-18): `Book.directory` remains, but identity moved to a minted `Book.id`. The "deferred, not rejected" UUID below is what ADR-17 adopts.*
**Date:** 2026-09-15
**Context:** The code-health pass before Part II of the feature map (docs/FEATURES.md, docs/HEALTH.md finding 2) found that a `Book` doesn't know where it lives: `scan()` and `search()` return Books whose only location hint is `formats[*].path`, and `Library` internally passes `(Path, Book)` tuples around. Every curation operation the TUI needs — mark reviewed, edit title/author, re-identify, supply a cover, merge, split, delete — starts with "which book", and without a handle on the `Book` itself each would have to take a separate directory argument that a title edit invalidates.
**Decision:** `Book` gains `directory: Path | None` — the book's folder in the managed library, `None` for a Book that has not been persisted yet. `storage.catalog.load_metadata` sets it, so `scan`, `search`, and `import_file` all return Books that carry it; `save_metadata(book, directory)` keeps its explicit `directory` parameter (the caller decides where a new book goes) and sets `book.directory` on success. `metadata.json` is unchanged: the directory is derivable from where the file was read, so there is no schema bump and nothing to migrate. `Library._existing_books` returns `list[Book]` and the folder lookup (`_find_book`, formerly `_resolve_directory`) reports the matched `Book`, not its path.
**Alternatives considered:** A minted UUID stored in `metadata.json` (schema v3) — deferred, not rejected: it is the right answer once anything *outside* the library needs to refer to a book across a rename (a TUI's saved selection, an external note, a sync log), but nothing does yet, and a UUID still needs a folder lookup for every operation, so it adds a schema version and a migration without removing the need for `directory`. Both at once — same reasoning; the folder handle is needed regardless, so it lands first. Keeping `(Path, Book)` tuples as the public shape — rejected: it leaks the storage layout into every signature.
**Consequences:** `Book`'s constructor grows an optional field (additive; no caller breaks). The identity changes when the title changes, because the folder is the title (ADR-1); an edit operation (FEATURES K2) therefore renames the folder and every `<folder name>.<ext>` and updates `book.directory` in one step. Expected follow-up, likely sooner than later: a UUID `id` field when the TUI needs a rename-stable reference — plan it as schema v3 with the usual migrate-on-read, and keep `directory` alongside it as the working handle. R3 (the persistence boundary) builds on this field: `Catalog.put(book)` can use `book.directory` when set.

### ADR-12: One `storage.store.Catalog` owns metadata.json + index; the index is keyed by folder name and updated per write
**Date:** 2026-09-15
**Context:** HEALTH.md finding 3. `Library` called `save_metadata` and then a full `rebuild_index` after every import — O(n) per file, O(n²) per bundle — and every future mutation (edit, merge, delete) would have had to repeat that pair by hand. The index also stored each book's *absolute* directory, so a moved library returned stale paths from `search` until something happened to delete the index file. And `Library` duplicated the "walk the root, load each metadata.json, skip the broken ones" loop that `rebuild_index` already had.
**Decision:** A new `storage/store.py` with `class Catalog(root)` is the single persistence boundary: `all()`, `get(directory)`, `put(book, directory=None)`, `search(query)`, `rebuild_index()`. `put` writes metadata.json and upserts *one* index row; `search` and `put` build the index lazily if it is missing or stale. `storage/index.py` rows are keyed by the book folder's name relative to the root (`name TEXT PRIMARY KEY`), never an absolute path, and the database carries `PRAGMA user_version = 2`; `is_current(db_path)` is false for a missing file, a pre-R3 unstamped index, or a non-database, and `Catalog` rebuilds rather than reads in every such case. `index.search` returns names; `Catalog.search` joins them onto `root` and loads the Books. `Library` keeps `scan`/`search`/`_persist` as thin delegations and holds no index path of its own. `Catalog` is internal (not exported); frontends use `Library`.
**Alternatives considered:** Incremental index maintenance inside `Library` without a store object (rejected — the next mutation would copy the pattern again; the point is one place). Dropping the sqlite index and searching `scan()` in memory (rejected for now — cheap at today's sizes, but the index is what FEATURES J4/J6 filters and ranking will build on, and keeping it costs one upsert per write). A `remove(directory)` on `Catalog` now (deferred to FEATURES K9, which owns the "what happens to the files" decision; `index.delete` exists for it). Storing the version stamp in a table instead of `user_version` (rejected — the pragma is the sqlite idiom and needs no extra schema).
**Consequences:** A bundle import rebuilds the index at most once (when none exists) instead of once per file; pinned by `test_store.py`. A library moved to a new path works on first `search` without manual repair; pinned by `test_library.py`. Existing pre-R3 index files are silently rebuilt on first use (they were always disposable). `index.search`'s return type changed from `list[Path]` to `list[str]` — an internal module, no public break. Hand edits to a library (adding a folder without `put`) still need `Catalog.rebuild_index()`; FEATURES M1/M2 will expose that through `Library`. The R4 provider abstraction and every Part II mutation now have exactly one persistence call to make: `Catalog.put`.

### ADR-13: Metadata lookup goes through a `MetadataSource` Protocol injected into `Library`; Open Library is the default implementation
**Date:** 2026-09-15
**Context:** HEALTH.md finding 4. `identify.resolve` imported `lookup_by_isbn`/`search` from `identify.openlibrary` directly and `Library` imported `fetch_cover` the same way, so the only way to keep tests off the network was to monkeypatch those module attributes by string — 51 such patches across four test files, brittle enough that ADR-9 had already recorded "tests now patch X instead of Y". The same hard wiring blocked three FEATURES items: a second source (N8, the only fix for E12-class missing covers), network configuration (N4), and offline import (L9). `OpenLibraryResult` was also the de-facto candidate type in `resolve`, naming a provider in provider-neutral code.
**Decision:** New `identify/source.py` defines the seam: `Candidate` (title/author/cover_url — `OpenLibraryResult` renamed), `MetadataSourceError` (the one exception a source may raise; a *missing* record is `None`/`[]`, not an error), the `MetadataSource` Protocol (`lookup_by_isbn`, `search(title, author=None)`, `fetch_cover`), and `NullSource` (knows nothing — offline, file-only imports). `identify.openlibrary` keeps its module functions as the HTTP client and adds `OpenLibrarySource`, a thin class over them; `OpenLibraryError` now subclasses `MetadataSourceError`. `identify(parsed, source)` takes the source explicitly; `Library(root, *, source=None)` defaults to `OpenLibrarySource()` and passes it to `identify` and to its own cover download. All five names are exported from `bookman`; the version goes 0.2.0 → 0.3.0 (the minor bump ADR-10 already scheduled). Tests: `tests/helpers.py` holds a `FakeSource` (scripted `record`/`results`/`cover`/`fail` attributes, recorded `calls`) and the shared EPUB/PDF builders; `tests/conftest.py` provides `source` and `library` fixtures. The only remaining string patch is the CLI's composition root (`bookman.library.OpenLibrarySource`), because the CLI constructs its own `Library`.
**Alternatives considered:** A module-level `set_source()` global (rejected — hidden state; two `Library` instances couldn't differ, and tests would leak). Making `Library` build the source from `Config` (rejected — `Config` is one field by design, ADR-8, and it would put network policy in the persisted file; an explicit constructor argument is the frontend's call, `resolve_library` stays about location only). An abstract base class instead of a Protocol (rejected — a Protocol lets a test double or a third-party source satisfy the contract without importing anything). Keeping `OpenLibraryResult` as an alias (rejected — nothing outside tests used the name, and the alias would only keep the provider name alive in `resolve`).
**Consequences:** A second source is now "implement three methods" plus a small composer that consults sources in order — the shape of FEATURES N8. Offline import (L9) exists today as `Library(root, source=NullSource())`; a CLI flag for it is a one-liner. Network configuration (N4: timeout, endpoint, user-agent) belongs on `OpenLibrarySource`'s constructor when it is needed. `test_real_books.py` runs on `NullSource` instead of a fixture full of patches. `identify()` grew a required parameter — it was never public. Deferred to R7: `formats.FormatParser` is still the dead Protocol noted in the Backlog; it will become the real parser registry there, alongside the public "supported suffixes" query.

### ADR-14: ISBN provenance — a text-scraped ISBN needs title agreement; a metadata-field ISBN keeps the either-agrees guard
**Date:** 2026-09-16
**Context:** FEATURES B6. `match_basis(same_isbn=True)` accepted an ISBN hit unless title *and* author both disagreed. That guard was built for checksum-passing junk numbers in PDF text, but the common PDF false positive is a *cited* book — the "Also by Cal Newport" page in Deep Work's front matter — which shares the author by construction, so the wrong book's ISBN and cover were accepted (the file's title survives per ADR-10, which masked it in `list` output). Tightening the guard to "titles must agree" for every ISBN would reject correct publisher ISBNs whenever Open Library's title differs from the file's: a volume's own title vs the set's ("The Fellowship of the Ring" vs "The Lord of the Rings Volume 1"), or an edition suffix (C7).
**Decision:** Provenance decides how much an ISBN is trusted. `ParsedMetadata.isbns_scraped: bool = False` says whether a parser found its ISBNs by scanning text (`parse_pdf` sets True) or read them from a structured field (`parse_epub`'s `dc:identifier`, the default). `match_basis` gains `isbn_scraped=`; with `same_isbn`, a scraped ISBN is rejected when both titles are present and disagree, regardless of author, while an asserted ISBN keeps the both-must-disagree rule. `identify` passes `parsed.isbns_scraped` through. A rejected ISBN is still dropped from the `Identification` (unchanged), so it never seeds grouping. A scraped ISBN with no file title to check against (a PDF with an empty info dict, A5/A7) is still accepted — there is no evidence against it.
**Alternatives considered:** Require title agreement for all ISBNs (rejected — regresses EPUB volumes and editions whose OL title differs, and drops their correct ISBN). Encode provenance as an enum or source string (rejected — one boolean answers the only question asked; an enum can replace it if a third provenance appears). Treat a scraped ISBN as no ISBN and rely on search (rejected — loses the ISBN basis on PDFs with an empty info dict, where the scraped ISBN is the only evidence). Apply the check in `resolve` rather than `match_basis` (rejected — the rule belongs with the other evidence rules, ADR-9, and `_find_book` may want it once `Book` carries provenance).
**Consequences:** B6 closes. B10's grouping check in `_find_book` runs the default (asserted) rule because `Book` carries no ISBN provenance — a scraped ISBN *unknown* to OL is kept (B7) and can still group with the author's other book; closing that residual means persisting provenance on `Book` (FEATURES I12). C7 widens slightly for PDFs: a correct scraped ISBN whose OL title carries or lacks an edition suffix is now rejected — safe direction, `needs_review`. `ParsedMetadata` gained a defaulted field and `match_basis` a keyword: additive, no minor bump on its own; a third-party `FormatParser` that never sets the flag gets the trusting default. Tests: six new across `test_match`/`test_resolve`/`test_library`/`test_pdf`/`test_epub`; F11's fixture was adjusted to a title-agreeing record because its old record disagreed on both fields with a scraped ISBN — exactly the shape this ADR rejects.

### ADR-15: Junk titles are graded in two tiers — a placeholder is no title; a generic title cannot match alone
**Date:** 2026-09-17
**Context:** FEATURES A12. `match_basis("Untitled", None, "Untitled", "X")` returned `TITLE_ONLY`, because the TITLE_ONLY path asks only for identical normalized titles when an author is missing on either side. Two unrelated files a converter left titled "Untitled" therefore grouped into one book, and a junk-titled file could accept an equally junk Open Library record. The gap summary proposed a stop-list turning such titles into "no title". A flat stop-list overshoots, though: "Book" and "Document" are named as junk in A12, but Alan Watts really did write *The Book: On the Taboo Against Knowing Who You Are*, which normalizes to "book" — a flat list makes that book permanently unidentifiable by title search, even when its author is known and agrees. A12's own wording scopes the scenario to a junk title *with no author*, and the damage it describes only occurs on the TITLE_ONLY path, which by construction runs only when author evidence is absent.
**Decision:** Grade junk titles by how much they could ever have meant. A **placeholder** — a normalized title built only from `_PLACEHOLDER_TITLE_WORDS` ("untitled", "unknown", "none", "no", "title", "default") possibly mixed with generic words and bare numbers, or a converter's filename stamp ("Microsoft Word - chapter1.docx", matched against the raw title before subtitle splitting eats it) — names no book at all: `normalize_title` returns `""`, so it compares exactly as a missing title, `titles_agree` is False for any pair involving one, and `identify` does not search for it. A **generic** title — built only from `_GENERIC_TITLE_WORDS` ("book", "document", "final", "draft", "new", "copy", "version", …) — survives normalization and is still searched, but `match_basis` refuses it on the TITLE_ONLY path via a new public `is_generic_title(normalized)`: it can only reach TITLE_AUTHOR, where an agreeing author does the real work. A title mixing junk words with a real one ("Untitled Poem", "The Book Thief") is neither tier. Neither tier vetoes a shared ISBN — a title that says nothing cannot contradict one, the same as a missing title always could not.
**Alternatives considered:** A flat stop-list blanking every junk title, per the gap summary's wording (rejected — costs the Alan Watts case and every book whose title reduces to one generic noun, with no matching gain, since A12's damage needs the TITLE_ONLY path). Shrinking the list to unambiguous placeholders only and dropping "book"/"document" (rejected — reopens half the gap: two files titled "Book" would merge again, and A12 names "Book" explicitly). Passing the author into `normalize_title` so it could decide both tiers in one place (rejected — `normalize_title` is a pure title→title function used for folder-independent comparison; the author belongs to the match rule, per ADR-9). Scoring titles by information content (rejected — a threshold to tune where a word list is legible and testable).
**Consequences:** A12 closes without a new false-negative class. The cost is a second concept in `identify/match.py`: `normalize_title` handles tier one, `match_basis` tier two, and a reader must know both to predict a match. `is_generic_title` is public within `identify.match` but deliberately not added to `bookman.__all__` — it is a matching internal, not frontend surface. Two files whose only title is the same generic noun *and* whose authors share a surname still group as TITLE_AUTHOR; that follows from the surname-only author rule already pinned as a known limitation, not from this ADR. A generic title now participates in the ISBN guard as "absent" rather than as a disagreeing title, which is a slight widening of C7 in the safe direction. Tests: seven in `test_match`, three in `test_library`, two in `test_resolve`.


### ADR-16: `docs/IDENTIFICATION.md` is the source of truth for identification; the code is bound to it by `SPEC_VERSION` and a conformance test
**Date:** 2026-09-18
**Context:** The identification spec was written after `docs/FEATURES.md` and its first draft was derived from that file's *Expected* column, which left the authority pointing the wrong way: FEATURES was the de facto source of truth and the spec a derived view of it. Nothing bound either to the code. FEATURES' promise that rows would cite the spec's step IDs was never wired — no row did — so the only way to audit "does the code do what we intend" was to read `match.py` and `resolve.py` again each time, which is exactly what a spec exists to avoid. Meanwhile the spec's `spec_version: 1` named nothing in the code, and its step IDs (MATCH-0..3, IDENT-1..6, GROUP-1..4) appeared nowhere outside the document.
**Decision:** Invert and bind. `docs/IDENTIFICATION.md` is the source of truth for the Identify and Group stages and the match rule they share; it derives from the ADRs only, and FEATURES rows named in its `sources:` are illustrative scenarios, not authority. `docs/FEATURES.md` Part I becomes the **conformance report** against it, with a `Step` column on all 86 rows of tables A–F mapping each scenario to the step it exercises (Parse/Place rows read `— (parse)`; tables G and H carry no Step, being outside the spec's scope). The code is bound three ways: `bookman.identify.SPEC_VERSION` names the spec version the package implements; every implementing function carries a `Spec:` line naming its step; and `tests/test_spec_conformance.py` enforces that every step is claimed by code in `src/` **and** cited by a ✅ row in FEATURES Part I, that `SPEC_VERSION` matches the document, and that all 20 rows of the spec's new decision table are what `match_basis` actually returns. Behavior changes go spec first (with an ADR), then code, then the FEATURES row — a rule now recorded in CLAUDE.md. Divergences are reported, never silently reconciled: the one open case is marked in `resolve.py` with a `DIVERGENCE` comment pointing at its row.
**Alternatives considered:** Leaving FEATURES as the source of truth and the spec as a derived view (rejected — a spec derived from the conformance report cannot check it; that is the inversion this ADR exists to fix). Making the YAML spec *executable* — a rules engine driving the match logic from data (rejected — the change history argues against it: ADR-14 and ADR-15 each added a new evidence *signal* rather than rewiring existing ones, so a table-driven engine would have been edited *and* required new Python predicates anyway; the complexity lives in `normalize_title`/`authors_agree`/`titles_agree`, which no rule table can express; and it would mean owning an interpreter against ADR-3's dependency posture, while costing the `sources:` and rationale prose that make the spec legible). Duplicating the step→test map into test-module docstrings (rejected — FEATURES' `Step` column already is that index; two copies drift). Re-exporting `SPEC_VERSION` from `bookman.__all__` (rejected — internal bookkeeping, and a public name is a semver commitment). Writing `spec_version` into `metadata.json` (deferred, not rejected — it would enable "re-identify every book identified under spec v1", which is the migration story for a future re-identify operation).
**Consequences:** The spec-first workflow is enforced by a test rather than by discipline, so the drift that killed the FEATURES cross-references cannot recur silently. FEATURES' `Step` column is load-bearing: a wrong Step cell now fails the suite. The decision table is executable spec — adding a matching rule means adding a row, and a bug means the code disagrees with a row that already exists. Cost: a behavior change now touches three places instead of one, which is deliberate friction, and 49 new tests (320 → 369). `SPEC_VERSION` bumps only when *intent* changes, never when code changes to conform to a step it already claimed. The first full audit under this regime (recorded in FEATURES "Conformance audit") found no unregistered divergence — the three known gaps (A10, D6, B6-residual) all already had rows, which is evidence the two documents were substantively right and only the wiring was missing.


### ADR-17: A Book's identity is a minted id stored in metadata.json (schema v3); the folder becomes a display name
**Date:** 2026-09-18
**Context:** ADR-11 made `Book.directory` the identity and listed a minted UUID as *deferred, not rejected* — right "once anything outside the library needs to refer to a book across a rename". That moment has arrived: the v1.0 slice is K1 (mark reviewed), K2 (edit title/author/isbn) and K3 (re-identify), and K2 renames the folder and every `<folder>.<ext>` inside it (ADR-1, ADR-10). With the folder as identity, the very operation a frontend performs most would change the book's id underneath every reference the frontend holds — a saved TUI selection, a pending edit, an in-flight re-identify. Doing this after K1–K3 would mean re-plumbing all three, so it lands first.
**Decision:** `Book` gains `id: str`, a `uuid4().hex` minted at construction and stored in `metadata.json`, which moves to `"version": 3`. `directory` stays exactly as ADR-11 defined it — where the book lives and its display name — but is no longer the identity. A pre-v3 file carries no id; rather than mint a fresh one per read (which would make the identity unstable before the first save, defeating the purpose) one is *derived* deterministically as `uuid5(namespace, folder_name)`, so every read of an un-upgraded book agrees, and it becomes a stored id on the next save. From that point it survives a rename. A stored id must be a non-empty string or the file is rejected as malformed, consistent with the existing `reviewed` check. Versions 2 and 3 are both readable; version 1 keeps its own migration path.
**Alternatives considered:** Keeping the folder as identity and having K2 return the new path (rejected — it makes every caller responsible for invalidating its own references, which is the bug this ADR exists to prevent, and it cannot survive a frontend that persists a selection between runs). Minting on read and writing back immediately (rejected — `load_metadata` would acquire a write side effect, and a `scan()` would rewrite an entire library just to read it). Deriving the id from the folder name permanently, with no stored value (rejected — that is the folder as identity again, wearing a hash). A monotonic integer (rejected — not stable across libraries, and merging two libraries would collide). Adding an `id` column to the sqlite index (deferred — the index is a disposable cache keyed by folder name per ADR-12, and nothing needs id lookup until J3, which is out of v1.0 scope; `scan()` already carries ids).
**Consequences:** K1–K3 can be built against a handle that a title edit cannot invalidate. `Book.id` is always set, so unlike `directory` it needs no `| None` handling at any call site. The public API gains a field, which is a minor version bump under the project's semver rule; `metadata.json` gains a schema version, migrated on read and upgraded on next save exactly as v1→v2 was. Cost: an id minted in memory is *not* yet durable — a Book constructed and never saved has an id nothing else knows about, which is correct but worth remembering when reasoning about `import_file`'s failure paths. The mixed uuid4/uuid5 origin is a wart, deliberately accepted to avoid write-on-read. J3 (get one book by id) remains unbuilt: with identity in place it is a small `scan()` filter, or an index column if it ever needs to be cheap. Tests: seven in `test_catalog` (round-trip, rename survival, distinctness, pre-v3 stability and upgrade, v1 migration, malformed id), three in `test_library` (per-book ids, id preserved when a second format joins, ids stable across `scan()` calls).


### ADR-18: Curation lives on `Library` as three operations; an edit sets `reviewed`; a title change renames files, then metadata, then the folder
**Date:** 2026-09-18
**Context:** ADR-4 chose "auto-lookup with a review flag, not a blocking confirmation", but only half of it was ever built: `Book.reviewed` was honored on import and nothing could set it. FEATURES K1–K3 are the missing half, and K2 carried an open design question — does editing a book implicitly mark it reviewed? The question turned out to have a forced answer. `_apply_identification` protects a reviewed book's fields and overwrites an unreviewed one whenever a later format identifies more strongly (F7). So an edit that did *not* set the flag would be silently discarded the next time another format of that book was imported: the correction would not be durable. Separately, K2 has to rename the book's folder and every `<folder>.<ext>` inside it (ADR-1, ADR-10), which is the first operation in bookman that mutates an existing book's layout on disk.
**Decision:** Three methods on `Library`, each taking a persisted `Book` and mutating it in place: `mark_reviewed(book, reviewed=True)` (K1), `edit(book, *, title=, author=, isbn=)` (K2), `reidentify(book)` (K3). `edit` distinguishes "not passed" from "passed as None" with a private `_UNSET` sentinel, so an author or ISBN can be *cleared* — a PDF whose `/Author` is "Adobe InDesign" is worth erasing (A13) — while `title` can only be replaced. An ISBN is validated and normalized to ISBN-13 on the way in; an invalid one raises `CatalogError` rather than being stored. **`edit` always sets `reviewed`**, for the durability reason above. `reidentify` runs the lookup unconditionally but applies it two ways: an unreviewed book adopts the result outright, while a reviewed book keeps every field the human set and gains only a cover it lacks and fields left empty — which is the route to a cover for an E12-class book (fix the title by hand, then ask again). It never changes the title, because the book's own title is what is searched on and wins over the source's (ADR-10), so it never needs to rename anything. A title change renames in this order: the format files inside the old folder, then metadata.json (atomically, via the existing temp-and-replace), then the folder itself — a single atomic `rename`, safe because stored filenames are relative and stay correct across it. `Catalog.relocate(old_name, book)` then moves the index row, writing the new row before dropping the old.
**Alternatives considered:** Letting a frontend mutate a `Book` and calling `Library.save(book)` (rejected — a far broader contract, with nothing stopping a caller from setting `id` or `directory`, and no place to validate an ISBN or reject a blank title). A `reviewed=` parameter on `edit` (rejected — a footgun: the only reason to pass False is to make the edit non-durable; `mark_reviewed(book, False)` afterwards is explicit about wanting the book back in the queue). `reidentify` refusing to run on a reviewed book, as the FEATURES row first suggested (rejected — it would make the primary workflow impossible, since `edit` sets `reviewed` and the whole point of fixing a title is to look it up again; respecting a review means not clobbering the human's fields, not refusing to act). Renaming the folder first and its contents afterwards (rejected — it puts the non-atomic stretch *after* the point of no return, so an interruption leaves metadata.json naming files that no longer exist; the chosen order leaves a book that loads correctly under a stale folder name, verified in-session). Moving contents into a freshly-`mkdir`'d folder instead of renaming (rejected — trades an atomic final step for a non-atomic one to close a name-claim race that the documented single-writer assumption already covers, M6).
**Consequences:** The review queue becomes actionable, which is what Phase 3's TUI needs. `Book.reviewed` now has two distinct meanings folded together — "checked and correct" and "edited by hand" — which is the ADR-9 collapse of per-field provenance (I12) showing through; if I10 user fields ever land, that is where to revisit it. A title edit has one genuine failure window: an interruption partway through the inner file renames leaves a folder whose metadata names files under the other name. That stretch is nothing but `Path.rename` calls with no I/O between them, and repairing it is FEATURES M2/M3, which do not exist yet — noted on those rows. Editing a title that sanitizes to the folder's existing name (or to the base of its `(N)` variant) deliberately does not move the book, so re-titling "Dune:" to "Dune" doesn't shuffle it sideways into "Dune (2)". The CLI does not expose any of this yet, so N7's parity claim now has a real gap. Tests: nineteen in `test_curation`.

### ADR-19: An asserted ISBN is rejected when the titles disagree and the author does not vouch for it
**Date:** 2026-09-18
**Context:** MATCH-1 (ADR-9) accepted a shared *asserted* ISBN unless title **and** author both disagreed, on the reasoning that a shared ISBN is a strong prior and either signal agreeing is enough to keep it. The first live run after the A10 fix showed the hole in that wording: a fabricated EPUB carrying `9780000000002` met an Open Library record titled "The three voices of poetry" with **no author**. The title contradicted the file's ("Deep Work"), the author could not disagree because there was none, so the record was accepted — `identified=isbn`, `needs_review=False` — with nothing at all vouching for the number. Conformant to the spec, and exactly the silent mislabel PR4 exists to prevent. The decision table had no row for "title contradicts, author silent"; rows 7 and 8 cover "nothing comparable on one side", which is a different case. This was found on Open Library data that is plainly junk under an unassigned ISBN, but a user's real file can meet the same shape: a mis-keyed `dc:identifier` landing on a record that lacks an author is the ordinary way a good-faith import goes wrong.
**Decision:** For an asserted ISBN, a title disagreement vetoes the match **unless the author agrees**. In terms of the existing guard: the reject condition becomes "titles both present, not generic, and disagree, and the author does not vouch" — where "does not vouch" means disagrees *or is absent on either side*. Everything else in MATCH-1 stands: a missing or placeholder or generic title still cannot veto (rows 7–9), an agreeing author still rescues a title mismatch (row 2), and the scraped-ISBN rule (ADR-14) is unchanged and remains strictly stricter. Spec: MATCH-1 outcome text amended and decision-table row 21 added (`Deep Work / Cal Newport` vs `The three voices of poetry / —`, asserted → none); `match_basis` changes `author_ok is False` to `author_ok is not True` in the asserted branch.
**Alternatives considered:** The fully symmetric rule — reject when *any* comparable signal disagrees and none agrees (the form first proposed in-session). Rejected because it also flips row 9 (generic titles, disagreeing authors → currently ISBN) on the strength of author comparison alone, and author comparison is the noisier signal: surname-only (D6), suffix-confused (D9), and routinely a publisher or tool name in PDF metadata (A13). Title is the signal ADR-14 already trusts to gate a scraped ISBN, so leaning on it here is consistent; author-only disagreement with no title to compare is left as it was, unobserved and unchanged. Leaving the rule alone and relying on ADR-10 to limit the damage (the file's title wins anyway, and a record with no author changes nothing). Rejected because the damage is not the fields: it is `identified=isbn` and a clean review flag on a book the automation got wrong, plus a junk ISBN retained where it can seed a GROUP-1 join.
**Consequences:** IDENT-3 and GROUP-1 both get stricter in the same way, since they share the rule (PR2). The visible effect on a real bundle is an ISBN that once accepted silently now being dropped and the file going to title search, where it is identified on its own merits or lands in the review queue — the PR4 direction. No accepted case in the existing suite changes; row 21 is new and executable. Tests: `test_match` gains the case; `test_spec_conformance` runs the row. FEATURES gains a B-table row citing MATCH-1. Not addressed: the observation that Open Library holds junk records under unassigned ISBNs in the `978000000000x` range, which is their data and not something a rule can fix; the corner-case bar remains "would a good-faith purchased file hit this", per the in-session note on scrutiny.

### ADR-20: CLI curation commands name a book by title, folder name or id; selection stays in the CLI, no `Library.get()` yet
**Date:** 2026-09-18
**Context:** K1–K3 landed on `Library` as operations taking a persisted `Book` (ADR-18), and the CLI had no way to hand one over, so N7's parity claim dropped to 🔶. Three things a user could plausibly type name a book, and none is ideal alone: `list` prints the *title*; the disk shows the *folder name*, which is the title sanitized (`Deep Work: Rules` → `Deep Work - Rules`) and suffixed `(N)` when shared; and `Book.id` (ADR-17) is 32 hex characters nobody will type by hand. J3 (get one book by id) is explicitly out of v1.0 scope.
**Decision:** Three subcommands, one per operation: `review BOOK [--undo]`, `edit BOOK [--title T] [--author A | --no-author] [--isbn I | --no-isbn]`, `reidentify BOOK`. `BOOK` is resolved in order: exact folder name, then `Book.id`, then exact title. Folder name and id come first because they are unique, so any book can always be named unambiguously; title comes last as the friendly form, and a title shared by several books is refused with their folder names listed. `edit` with no field flag exits 2 rather than silently only setting `reviewed` — that is `review`'s job. Selection is a private CLI helper (`_find_book`) filtering `Library.scan()`; nothing was added to `Library`'s public surface. Command names are `review`/`edit`/`reidentify` — `edit` and `reidentify` match the methods, `review` reads as the verb `mark_reviewed` is.
**Alternatives considered:** Id only (rejected — `list` would have to print ids and the CLI would be unusable by hand; it is what a TUI would do, not a person). A search query that must match exactly one book (rejected — friendliest to type but fragile: it breaks the day a second Newport book is imported). Adding `Library.get(id)` now (rejected — that is J3, out of v1.0 scope, and the folder-name and title fallbacks are CLI ergonomics rather than library semantics; ADR-6's "no logic the TUI would duplicate" does not bite because the TUI holds `Book` objects and never resolves a typed name). `set` (FEATURES' earlier wording; too generic next to `config`) and `mark-reviewed` (exact parity, longer to type) as names.
**Consequences:** N7 returns to ✅ and v1.0 has one fewer unblocked item. The CLI imports `_UNSET`/`_Unset` from `library` to forward "not passed" vs "clear" for author and ISBN — same-package private use, accepted as a small wart over widening `edit`'s contract. When the TUI needs get-by-id, that is J3 on `Library`, and the CLI's id branch should move onto it rather than stay a parallel `scan()` filter. Title matching is exact and case-sensitive by design — no fuzzy selection, so a command never acts on a book the user did not name. Every command re-`scan()`s the library to resolve `BOOK`, which is fine at personal-library scale and is what J3 would make cheap if it ever mattered. Tests: sixteen in `test_cli` (selection by each of the three forms, the ambiguous-title refusal, unknown name, missing library not created, each `edit` flag including clearing, invalid ISBN, no-field usage error, mutually exclusive flags, `reidentify` with and without a hit, help text).


### ADR-21: One file per format kind; a conflicting same-kind file is refused with the evidence, never overwritten
**Date:** 2026-09-18
**Context:** FEATURES F14 / spec OQ1: a second file of a kind the book already holds — two EPUB editions, or two unrelated books that grouped wrongly — silently overwrote the first, because `_place_format` copied unconditionally. Reproduced in-session by accident: two *Dune* EPUBs by "Frank Herbert" and "Brian Herbert" grouped (author agreement is surname-only, a known limitation) and the second destroyed the first. OQ1 had been recorded as blocked on stored per-file provenance (I11, a hash) to tell "the same file again" (F13, which must stay idempotent) from "a different file of the same kind". That premise was wrong: the existing file is right there in the folder, so a byte comparison against it answers the question with no stored provenance at all.
**Decision:** GROUP-4 gains a first rule (spec_version 1 → 2): a book holds at most one file per format kind, and a file whose kind the book already has is **refused** unless it is byte-for-byte the file already there. Refusing changes nothing — not the folder, not the catalog, not the book's evidence. `Library.import_file` raises `FormatConflictError(BookmanError)` carrying what a person needs to resolve it: the `Book` that was joined, the path of the file it already holds, the `MatchBasis` of the join (an ISBN join means "same book, which file do you want?"; a title-only join means "was this even the same book?"), and what the incoming file resolved to. `Library.import_directory` collects these in a new `ImportBatchResult.conflicts` list rather than `failed`, because a conflict is a policy refusal awaiting a decision, not an error in the file, and a frontend iterates it to prompt. The CLI prints each one with the basis and a hint. The resolution itself — replace the file, or import it as a separate book — is deliberately *not* built now; the user's call was that the refusal with its message is enough for v1.0.
**Alternatives considered:** Keep both files as versions, `Title (2).epub` (rejected — breaks one-file-per-kind, which the model, the folder layout and the TUI all assume, and leaves a wrong merge holding two files under one title). Accept and report (rejected — the first file is still gone, just noisily). Report the conflict through `ImportBatchResult.failed` to avoid a new field (rejected — it misnames a decision as an error, and a TUI would have to type-check exceptions to find the prompts). Building `import_file(path, replace=True)` and "import as a separate book" alongside (deferred, not rejected — small, but scope the user chose not to take on now).
**Consequences:** F14 closes ✅ and L6 improves: re-running a bundle import is idempotent, and a changed file is refused rather than clobbering. Nothing is ever lost on import — the first time that can be said for every path through `import_file`. Two follow-ups become named, unbuilt operations: **K11** (replace a book's file for one kind deliberately) and **K12** (import a file as a new book, bypassing GROUP); until they exist, a refused file that the user *does* want needs the manual workaround of deleting the file in the folder and importing again, which the CLI hint states. The public API grows an exception class and a dataclass field, a minor bump. Cost: a same-kind re-import now reads both files fully to compare before deciding; at ebook sizes that is negligible next to the network lookup that precedes it. The check runs *after* identification, since `_find_book` needs the incoming file's resolved title/author/ISBN to find the book at all — a refused file still costs one lookup.

### ADR-22: The file's own author wins over the record's on any accepted match; the record's author is kept as `record_author`; a stand-in author ("Unknown", "N/A") is no author
**Date:** 2026-09-18
**Context:** Seen live 2026-09-18: an EPUB whose `dc:creator` was "Martin Luther King Jr." was identified on a corroborated match and came out as "Martin Luther King Jr., J.D. Jackson" — the audiobook narrator. IDENT-6 (ADR-9) let the record's author *replace* the file's whenever the match had corroborated it (ISBN or TITLE_AUTHOR), and Open Library's search returns *work*-level `author_name`: the union of contributors across every edition of the work, with no role field anywhere in the API that would let a rule tell a narrator from an author. Every lookup route returns the same polluted list, so no source-side filter fixes it. The user's framing: when only one side has an author the choice is an OR; when both do, it is a formatting preference (file's "King, Martin Luther, Jr." vs. the source's "Martin Luther King Jr."), which belongs to the person, not the library — and author is not structural (ADR-1: title-named folders), so nothing on disk depends on the answer.
**Decision:** (1) IDENT-6 now reads for the author exactly as it does for the title (ADR-10): the file's own author stands on any accepted match, and the record's is used only when the file has none. The old distinction by basis is gone — `_accepted` is `parsed.author or record.author` on every branch. The argument is ADR-10's: a match that corroborated the author has already checked the file's against the record's, so replacing it gains nothing; and the file names who wrote *this* edition, while the record names everyone attached to the work. (2) The record's author is kept beside the book's own as `Book.record_author` (metadata.json schema 3 → 4, read back as None from older files), carried from `Identification.record_author`. It follows the same adoption rule as the record's other fields — set when a file's identification is adopted, untouched when it is not, refreshed by `reidentify` — and it is provenance, not a second opinion: a difference between the two does *not* surface the book for review. This reverses ADR-10's "deferred as YAGNI until the TUI asks" for the author field, because the TUI's author has now asked. (3) A file author that is only a stand-in for a missing value — "Unknown", "Unknown Author", "N/A", case-insensitive, the whole string — is treated as no author at the start of `identify`, so it is filled from the record rather than kept and never reaches the catalog. "Anonymous" and "Various" are *not* stand-ins: they say something true about the book (Lazarillo is anonymous; an anthology is various) and are kept like any other author. Both kinds remain no evidence at MATCH-2, which is unchanged. `spec_version` 2 → 3.
**Alternatives considered:** Keep record-wins and filter narrators out of the Open Library response — impossible, there is no role field on `/search.json` or the work record, and OL is meant to be one `MetadataSource` among several (ADR-13, PR5) so a vendor-specific heuristic would be the wrong layer anyway. Take the *intersection* of the two author lists on a corroborated match — rejected: it re-derives what the file already says at the cost of parsing author lists, and loses the record's spelling entirely, which the frontend wants to offer. Flag a file/record author disagreement for review — rejected: sort-order vs. display-order differences ("King, Martin Luther" / "Martin Luther King Jr.") would flag most of a library for a formatting question. Sanitize stand-ins in the format parsers — rejected: `ParsedMetadata` is "what the file says" (its docstring), and the usability judgement already lives in `identify` for titles (IDENT-4's `is_usable_title`), so the author judgement sits beside it. Treat "Anonymous" as a stand-in too — rejected: it would replace a true statement with a TITLE_ONLY record's uncorroborated editors, the exact outcome `test_resolve::title_only_match_keeps_the_files_author` pins for Lazarillo.
**Consequences:** The MLK book identifies as "Martin Luther King Jr." with `record_author="Martin Luther King Jr., J.D. Jackson"`, which a frontend may show as "Open Library says …". Files with a wrong or sloppy author of their own — a misspelling, a publisher's name in `dc:creator` (A13) — are no longer corrected by a corroborated lookup; they keep what they had and the correction is one `edit` away, with `record_author` on hand to copy from. That trade was made knowingly: narrator pollution has been observed, sloppy-but-present authors that a lookup would have fixed have not. A file saying "Unknown" now gets the record's author on any accepted match, including TITLE_ONLY, where it is uncorroborated — acceptable because "Unknown" carried nothing to lose and TITLE_ONLY surfaces for review regardless. Schema 4 adds one optional key; v2/v3 files load unchanged and upgrade on their next save. `Book` gains a field (minor bump). FEATURES D13 (narrator) and D14 (stand-in author) are the new rows; I12 moves from 🔶 to partial for the author field. `reidentify` on a reviewed book still refreshes `record_author`, since it is the source's statement rather than a human's field.

### ADR-23: A different edition is a different book; MATCH-0 lifts an ordinal edition marker out of the title before normalization and compares it like a volume number
**Date:** 2026-09-19
**Context:** Spec OQ3 / FEATURES C7 asked whether "Algorithmic Thinking, 2nd Edition" and "Algorithmic Thinking" are the same book, and recorded that today's code says "no" by accident. Checked 2026-09-19, the accident was worse than recorded: the answer depended on punctuation. After a comma or a bare space the marker survived `normalize_title` and the titles differed; after a colon it was dropped as a subtitle, and in brackets it was dropped as an "edition note" — so `Algorithmic Thinking (2nd Edition)` and `Algorithmic Thinking: 2nd Edition` both matched the first edition TITLE_AUTHOR and would have merged into its folder (silently if the first edition had only a PDF; as a misleading ADR-21 conflict if it had an EPUB). PR4 names that the worst outcome. The question also blocks K12 and I7, and the user asked to settle it.
**Decision:** Yes — a different edition is a different book. MATCH-0 gains a first rule (spec_version 3 → 4): an *ordinal* edition marker — a numeric or spelled-out ordinal followed by "edition" or "ed." ("2nd Edition", "Second Edition", "2nd ed."), wherever it sits and however it is set off — is lifted out of the title *before* the subtitle and bracket rules can discard it, reduced to its number, and appended to the normalized title as `edition N`. From there the existing "fuzz never bridges a number" rule of MATCH-2 (ADR-9, C17) does the work: two marked titles must carry the same number, and a marked title does not agree with an unmarked one — an unmarked title is *not* assumed to be the first edition, because the safe direction under PR4 is apart. Decision-table rows 22–27 pin every punctuation shape, the spelled-out form, two differing markers, and the ISBN route. The unspecified list gains ordinal-less markers ("Revised", "Expanded", "Anniversary", "2e"), which are not recognized until one is seen in a bundle.
**Alternatives considered:** Editions group under one book with an edition field (I7) — rejected for v1.0: one file per kind (ADR-21) means two editions each with an EPUB cannot share a folder, so this needs per-edition file slots, a model and layout change, and editions carry their own ISBNs and covers anyway. Treat marker-vs-unmarked as agreement (an unmarked title "says nothing" about edition, like a missing title says nothing about an ISBN) — rejected: first editions are almost never marked, so that reading merges exactly the pair OQ3 asked about; the cost of the strict reading is the reverse case, a 2nd-edition EPUB whose companion PDF carries a bare `/Title`, which still groups when the PDF's scraped ISBN matches (GROUP-1's asserted-ISBN rule, since OQ2 leaves the book's ISBN provenance unknown) and otherwise lands as a second folder, visible and mergeable later. Recognize edition markers only after a comma, leaving the bracket and subtitle rules alone — rejected: that is the bug, not a policy. Strip the marker for identification (IDENT-5, where the source's title is the work's and never carries one) but keep it for grouping — rejected: PR2, one rule for both questions; the ISBN route already identifies an edition file against the edition record (row 27), and a search miss is a missing cover, not a wrong merge.
**Consequences:** C7 closes ✅ and OQ3 moves to `decided_questions`. Grouping of editions is now punctuation-independent in the safe direction. An edition file with no ISBN identifies by search only when the candidate's title carries the same marker, which Open Library's work-level search titles usually do not — the same bucket as the series-prefix gap (C10): a cover not fetched. K12 (import as a separate book) inherits a clear meaning: "different edition" and "different book" are the same thing. I7 (edition as a field) stays open but is no longer a grouping question — it would be display metadata parsed from the marker MATCH-0 already isolates. `normalize_title`'s output changes for marked titles (`… edition 2` appended), which is internal; no schema change. `SPEC_VERSION` 3 → 4.

### Public API
- `Library` — the main entry point: `Library(root)`, `.import_file(path) -> Book`, `.scan() -> list[Book]`, `.search(query) -> list[Book]`.
- `Book`, `BookFormat` — value objects for a logical book and one of its on-disk format files.
- `FormatKind` — `epub` | `pdf` | `mobi` (mobi has no parser yet; see ADR-2).
- `MatchBasis` — `isbn` | `title_author` | `title_only`: the evidence behind `Book.identified` (how the Open Library record was matched to the file; None = file-only metadata) and `Book.grouped` (weakest evidence that ever joined a second format into the folder; None = nothing grouped). `Book.reviewed` marks a human-confirmed book that imports must not overwrite; `Book.needs_review` derives the review flag from the three. See ADR-4 and ADR-9.
- `UnsupportedFormatError` — raised by `Library.import_file` for a file extension with no registered parser.
- `Config`, `config_path()`, `load_config()`, `save_config()`, `resolve_library()`, `LibraryNotConfiguredError` — the persisted "where is my library" setting; see ADR-8. A frontend should call `resolve_library(explicit_override)` to get the root to hand to `Library(...)`, and `save_config(Config(library=...))` when the user picks a new one.
- `formats.*`, `identify.*`, `storage.*` remain internal — `Library` is the intended surface for a consumer like the TUI.

### Compatibility and versioning
Python 3.10+. Semantic versioning: patch for fixes, minor for new public API (new exports from `bookman/__init__.py`), major for breaking changes to any exported symbol's shape or behavior.
